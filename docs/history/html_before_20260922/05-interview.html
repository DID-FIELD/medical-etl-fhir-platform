六个高频追问

Q1：你的数据哪里来的，有多少？

使用 Synthea 官方合成医疗样本，不是医院生产数据。本机下载的压缩包约 5.68 MiB，含 18 个 CSV。患者表 108 行、就诊表 5,571 行、影像实例 478 行；这些实例对应 413 次检查和 96 位患者。不能把文件总行数说成独立患者数。

Q2：你实际跑出了多少数据？

当前已落地 108 位患者、5,571 次就诊、413 次检查、413 个序列和 478 个实例。患者汇总与概览各 108 行，保留 12 位无影像患者；数据库与 API 的 17 项完整样本核验通过。

Q3：为什么原来 478 行，后来只有 413 条？

源文件是影像实例粒度，一项检查可以有多个实例；下游检查事实按检查标识归并，所以变成 413 次检查。差值 65 不是无效数据数，必须区分粒度变化和数据过滤。

Q4：你怎么关注数据的流转？

已记录批次、源文件校验值、源记录序号、处置结果和各层数量，并用稳定键关联患者、就诊和检查。实例保留源位置，可从检查 API 回查到全部源实例；数据库加载前后均做对账。每一步还要区分同粒度过滤、JOIN 展开和聚合变化。

Q5：为什么要做 ODS、DWD、DWS、ADS？

ODS 为重放与追溯保留来源；DIM 管理统一患者维度；DWD 保留可复用的业务事实；DWS 提供公共统计；ADS 服务具体查询。每层要有明确粒度和职责，而不是为了目录看起来完整。

Q6：有没有大数据量性能结论？

已有万人合成归档的单机实测：Python 流式 ETL 约 393 秒、281 MiB；完整 Spark 约 283 秒、2.52 GiB，但 Spark 时间包含回读和对账。没有多机集群性能结论，也不能据不同计时范围直接计算加速比。

如何组织一个真实的问题案例

现象：在什么数据与命令下出现什么问题？
证据：哪份日志、测试或数量对账能证明？
原因：哪个字段、粒度、规则或写入阶段造成？
处理：具体改变了什么，为什么这样处理？
验证：同样输入重跑如何？回归测试是否通过？
边界：还没覆盖什么，不应该推广成什么结论？

未解决的问题也可以诚实解释定位过程。不要为了案例完整，编造修复或生产事故。

试着不看答案讲一次

  1. 用 60 秒介绍项目目的、数据与当前完成度。
  2. 用 2 分钟解释一条检查从源文件到汇总的过程。
  3. 解释“患者少了 12 位”和“实例少了 65 行”为什么不是同类问题。
  4. 说出两项已经验证的事实，和两项尚未验证的能力。
  5. 选择一个真实问题，按上面的六步组织答案。
