数据流转 · 教学示例

先认识记录的层级

一位患者 → 多次就诊 → 多次检查 → 多个序列 → 多个影像实例。

本章使用虚构标识讲解，不是已下载数据中的真实行，也不是实测结果。示例：患者 P-DEMO 在就诊 E-DEMO 中有两次检查。检查 S-01 有两个 CT 实例，检查 S-02 有一个 MR 实例。

患者 P-DEMO
└─ 就诊 E-DEMO
   ├─ 检查 S-01（CT）
   │  └─ 序列 SE-01 → 实例 I-01、I-02
   └─ 检查 S-02（MR）
      └─ 序列 SE-02 → 实例 I-03
1 位患者 ≠ 1 次就诊 ≠ 2 次检查 ≠ 3 个实例
STEP 01 / SOURCE

接入：先认识表，再关联

源表本例记录关联方式
patients.csvId = P-DEMO；性别、出生日期等患者键
encounters.csvId = E-DEMO；PATIENT = P-DEMO通过 PATIENT 找患者
imaging_studies.csv3 条实例行；Id 分别为 S-01、S-01、S-02PATIENT → 患者，ENCOUNTER → 就诊；SERIES_UID / INSTANCE_UID 标识层级

需要做：保存原始包，盘点文件大小、行数、字段和校验值。先确认实际键的唯一性与一对多关系，再定义转换。

为什么不直接把三个表 JOIN 之后统计行数？

一位患者会匹配多条检查实例，JOIN 后出现多行是正常的一对多展开。如果此时 COUNT(*)，得到的是展开后的行数，不能说是患者数或检查数。应先选定目标粒度，再按对应键去重或聚合。

STEP 02 / ODS

ODS：保存原始形态与来路

计划为三张源表分别保留 ODS 数据。原始值与标准化值分开保存，便于重跑和排查。

业务字段：Id、PATIENT、ENCOUNTER、DATE、SERIES_UID、INSTANCE_UID…
追溯字段：batch_id、source_file、source_sha256、source_row、ingested_at

本例输出：患者 ODS 1 行、就诊 ODS 1 行、影像 ODS 3 行。此时不把两条 S-01 当成重复检查删掉，它们是不同实例。

“ODS 原样保留”是目标设计。原项目主流程实际在清洗后写 ODS，分步流程还存在不同处理方式；这部分语义需要在实施时统一。
STEP 03 / QUALITY

校验：决定记录能否进入可信明细

字段有效键不缺失，时间可解析，代码和字段类型符合约定。
关系一致患者存在、就诊存在，检查所属患者与就诊所属患者一致。
重复可解释相同实例重复导入需要去重；不同实例属于同一检查应保留。

通过的进入明细；不通过的保留源位置和原因；相同业务键却内容冲突的记录按明确策略处置。本例假定全部合格，仍保留 3 条实例。

如果某条记录同时日期非法、患者键缺失，怎么计数？

它可以触发两项规则，但在“隔离记录数”里只计一次。规则失败次数与失败记录数必须分开，否则对账会重复扣减。

一次失败应该直接重跑吗？

先判断原因：输入缺字段、关联错误等需要处理数据或配置；临时连接故障才可能靠重试恢复。写入还必须保证失败批次不会被当作成功结果发布。

STEP 04 / DIM + DWD

维度描述“谁”，事实记录“发生了什么”

计划模型一行代表什么本例输出
患者维度一位有效患者，统一的下游患者键1 行；P-DEMO 映射为 PID-DEMO（仅示意）
就诊事实一次就诊1 行；E-DEMO 关联 PID-DEMO
检查事实一次影像检查，按源检查键2 行；S-01 / S-02
实例关联一个实例到所属检查和序列的关系3 行；保留 I-01、I-02、I-03 的来路

身份处理：患者标识映射必须跨表一致，否则关系会断裂。姓名、精确出生日期等直接标识信息限制流转，原始键映射留在受限追溯区。已有截断哈希只属于原型实现，不能宣称完全匿名或生产级隐私保护。

3 条实例 → 2 次检查，是粒度归并。实例仍有独立关联记录，不能把这次变化说成丢掉了 1 条脏数据。
STEP 05 / DWS → ADS

先定义公共统计，再服务具体问题

DWS：患者检查统计（本例）
patient_key = PID-DEMO
exam_count = 2
modality_count = 2
latest_exam_time = 两次检查时间中的较晚值

ADS：患者检查概览
患者维度 LEFT JOIN 患者检查统计
→ 展示患者信息、检查次数、最近检查与检查列表入口

没有检查的有效患者仍可保留在 ADS，检查次数填 0。不要使用内连接无意删除他们。跨模态统计要明确：一项检查有多个模态时，它可能出现在多个分组中。

STEP 06 / SERVICE

对外查询，同时能向后追溯

API 从患者维度、检查事实或 ADS 读取合适结果。FHIR 可以从 DIM / DWD 映射，不必先绕过所有汇总层。

计划评审的语义：患者 → Patient；就诊 → Encounter；影像检查 → ImagingStudy；生命体征/检验观察 → Observation。具体字段、版本和校验规则需在实施前确定。

应用中的“检查次数 = 2”
 → DWS 中 PID-DEMO 的汇总
 → DWD 中 S-01、S-02
 → 检查与实例关联 I-01、I-02、I-03
 → ODS 源表 + 文件校验值 + 行位置
 → 原始 Synthea 文件
本例是教学示意；C 阶段已实际实现三表关联及检查到源实例的 API 追溯，真实样本验证见最新报告。
