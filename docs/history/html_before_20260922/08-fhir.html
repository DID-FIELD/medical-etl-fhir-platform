字段如何映射？

数仓字段FHIR 字段明确的处理规则
patient_key / gender / birth_yearPatient.id / gender / birthDateM/F → male/female；其他 → unknown；出生日期只导出年份，不补造月日
encounter_key / patient_keyEncounter.id / subject引用 Patient/{patient_key}，目标必须存在
start_at / stop_atEncounter.period / status有结束时间映射 finished；无结束时间用 unknown，不擅自声称正在就诊
encounter_classEncounter.class / typeclass 采用 Synthea 官方映射；type 保留原始类别；遇到新类别拒绝导出，等待补充规则
study_key / patient_key / encounter_keyImagingStudy.id / subject / encounter检查与其就诊必须归属同一患者
started_at / 序列与实例明细started / numberOfSeries / numberOfInstances / modality独立统计序列与实例；模态去重，多模态不拆成多个检查
就诊类别的对照

ambulatory、outpatient、wellness、urgentcare → AMB；inpatient、snf → IMP；emergency → EMER；home、hospice → HH；virtual → VR。这是针对 Synthea 的规则，不应无条件套用所有医院数据。

资源 ID 沿用数仓稳定键，可从资源回到对应 DWD。患者不导出姓名、地址、证件或完整生日；这只是本项目的字段最小化，不构成生产数据匿名化认证。

实际遇到的问题：CSV 没有检查 UID

CSV 的 Id 是检查业务标识；SERIES_UID 和 INSTANCE_UID 是另外两个层级。不能把业务 UUID 直接声称为 DICOM StudyInstanceUID，也不能从子级 UID 猜出父级 UID。

R4B 要求带 series 元素的 ImagingStudy 同时提供 DICOM 检查 UID。这次采用摘要导出：保留检查引用、时间、模态和数量，省略 series、DICOM identifier 与像素访问 endpoint。完整序列/实例仍在数仓。

ImagingStudy.status 使用 unknown，因为 CSV 没有影像服务可用性状态。后续若取得同一批次的可靠 StudyInstanceUID 对照，可再扩展完整层级导出；新增数据不能靠编号猜测关联。

依据：HL7 R4B ImagingStudy 字段定义。

怎么证明数据没有流转错？

  • 导出前：源快照必须 SUCCESS，五张输入模型表的 SHA-256 必须与原清单一致。
  • 映射后：每类资源 ID 与对应数仓主键集合、记录数一致，无重复。
  • 关联：Encounter 的患者存在；ImagingStudy 的患者和就诊存在，并且患者归属一致。
  • 语义：数量、时间、类别与数仓映射一致，没有人为补造检查 UID 或图像服务地址。
  • 落盘后：NDJSON 回读再校验，记录产物哈希、源批次、源清单哈希、导出代码哈希和模型包版本。
失败与重跑如何处理？

新增 10 项测试覆盖错引用、错患者、错数量、重复 ID、多模态、零影像、未知类别、源文件篡改与重复导出。同样源数据导出的资源文件哈希一致；目标目录已存在时拒绝覆盖。写入中失败的清单标记 FAILED，消费方只接受 SUCCESS；失败不会修改原数仓或数据库的当前批次。

验证范围是 Python R4B 模型与项目规则。尚未运行官方 HL7 Validator、术语服务或 US Core Profile 验证。NDJSON 文件不等于实现了 FHIR Bulk Data 协议，也不等于已经部署 FHIR 服务。

面试时可以这样讲

“我用 Synthea 合成数据跑了三张表，共 6,157 条源记录。影像表按实例展开，478 条不能直接当作检查次数；分层后是 413 次检查。数仓既提供患者概览查询，也导出 6,092 个 FHIR 资源。我通过批次号、文件哈希、源行号和引用校验检查数据流转。”

“转换时发现 CSV 缺少检查层的 DICOM UID。我先确认标准要求，选择输出检查摘要，把完整实例留在数仓，明确记录哪些能力还不能提供。这比只把字段改名更接近实际接入问题。”

所有数字是这份小样本的实测结果；千/万患者规模、并发性能与像素读取能力仍不能宣称已验证。
