# 医疗 ETL 项目完善规划：基于 Synthea

日期：2026-09-18
状态（2026-09-25）：Stage M 万人完整 Spark→FHIR/数据库 DAG 已通过，详见 [当前交接](HANDOFF_STAGE_M.md)；下文早期规划与历史基线保留供复习。

## 1. 目标与边界

目标是把现有医疗 ETL / FHIR 原型完善成一个能复现、能对账、能讲清楚的数据工程项目。面试时能用实际证据回答：数据从哪来、规模多大、如何流转、输出多少、为什么数量变化、如何定位失败和验证重跑。

数据源确定为 Synthea。公开样本和自行运行 Synthea 生成的数据都属于合成医疗数据，不代表医院生产数据。规模测试主要使用 Synthea 生成的数据；人工修改的小样本只用于故障注入，单独标注。

沿用现有 Python、PostgreSQL、分层数仓、FHIR 和 API 的项目方向，先补齐业务语义与验证。Spark 放在相同口径的对照实验阶段，Airflow 放在链路稳定后的调度验证阶段。当前不增加新的大数据组件、不开展影像像素处理，也不开发自动驾驶项目。

## 2. 先确定业务问题

主线：一个患者有哪些就诊，在就诊中做了哪些影像检查，这些检查的时间、类型和频次如何统计？

首批展示三个结果：

1. 患者检查概览：检查次数、最近检查时间、检查类型分布。
2. 检查量分析：按日期、影像模态统计检查数和涉及患者数。
3. 数据处理质量：每批输入、异常、重复、有效记录及各层落地数量。

先把这条链路做完整，再考虑加入生命体征或检验指标，不一次接入全部源表。

## 3. Synthea 数据选择与映射

| 优先级 | 源文件 | 用途与粒度 | 关键设计 |
| --- | --- | --- | --- |
| 第一批 | patients.csv | 患者维度，一位患者一条 | 保留源患者键，提供一致的下游替代键 |
| 第一批 | encounters.csv | 就诊事实，一次就诊一条 | 就诊关联患者；保留完整起止时间 |
| 第一批 | imaging_studies.csv | 影像元数据，区分检查、序列、实例 | 按源检查标识建检查事实，序列/实例单独保留关联 |
| 第二批 | observations.csv | 测量/观察事实 | 保留代码、类型、值、单位、时间及就诊关联 |

先对下载到的文件做剖析，确认实际列、空值、主外键和重复情况。数据字典是设计依据，实际文件是验证依据。

不能直接将所有源记录压成原有六列 CSV：这样会丢失就诊键、检查键、完整时间和影像层级。之前六列适配试跑只用于探索，不作为最终数仓契约。

### 数据集分级

- 小样本：使用已下载官方 CSV 样本理解关系并做正确性验证。
- 中规模：计划使用固定配置生成约 1,000 位患者的 Synthea 数据，记录实际导出患者数及每表记录数。
- 较大规模：中规模通过后再评估约 10,000 位患者的生成与测试，依据本机资源控制范围。
- 故障样本：从一份小样本复制出独立版本，按清单注入异常，不修改原始数据。

患者生成目标不是事实表行数，不能提前宣称会得到 10 万次检查。记录生成版本/提交、种子、参考日期、地区、配置、执行命令与导出格式；保存原始包 SHA-256，避免 latest 下载链接变化后无法复现。

## 4. 建议的数据流程与分层

```text
Synthea CSV 原始包 + 来源清单
          ↓
ODS：按源表保留原始字段、源文件与批次
          ↓
类型与时间标准化 → 质量校验 → 异常隔离 / 重复处理
          ↓
DIM：患者等维度
DWD：就诊事实、影像检查事实及源实例关联
          ↓
DWS：患者检查汇总、日期与影像模态统计
          ↓
ADS：患者检查概览、检查量分析、批次质量报告
          ↓
SQL / API 查询；按明确标准映射 FHIR 资源
```

| 层 | 计划内容 | 数量口径 |
| --- | --- | --- |
| ODS | 患者、就诊、影像源记录 | 每张源表分别与输入对账 |
| DIM | 患者维表 | 建议覆盖全部有效患者，包括没有影像检查者 |
| DWD | 就诊事实、检查事实、实例关联 | 分别统计就诊、检查、实例，不能相加称为检查数 |
| DWS | 患者及日期/模态聚合 | 检查数按检查键统计；跨模态去重口径单独说明 |
| ADS | 检查概览与分析结果 | 从已核对的事实与汇总生成，允许零检查患者 |

若一次检查含多个模态，按模态分组的总和可能大于去重检查总数。采用多值关联还是主模态归类，需要在建表前明确，不能让 JOIN 无意放大数据量。

实现上先选一条可验证的主链路：优先复用现有 PostgreSQL 作为落地和 API 数据源；若连接环境暂未恢复，文件快照可用于算法验证，但不能据此声称数据库链路已通过。Spark 之后使用同一数据版本进行分层结果对照，不同时维护两套不同业务规则。

## 5. 数据质量、流转与重跑设计

### 质量规则

- 结构：必需列、字段类型、源键完整性。
- 关联：就诊属于已知患者；影像检查引用的患者、就诊应存在且关系一致。
- 时间：格式、时区、缺失与先后关系；保留源时间，日期仅作为派生字段。
- 重复：区分完全重复、相同键不同内容、合法的一对多实例记录。
- 属性：相同患者冲突的属性如何处理；不能无说明地任取一条。
- 输出：事实外键完整、FHIR 资源标识唯一且引用可解析。

### 每批应留下的证据

- 来源清单：数据集版本、文件数、压缩/解压字节数、每表行数、校验值。
- 运行清单：批次 ID、代码版本、配置、开始结束时间、状态、运行环境。
- 逐阶段指标：输入/输出/异常/重复行数、关联失败数、耗时、输出大小。
- 追溯关系：源文件校验值 + 源表 + 源行位置 + 业务键 → 事实键 → 聚合/服务结果。
- 异常明细：原始位置、失败规则、处理方式；源标识等敏感字段只保留在受限追溯区。

同一粒度、互斥处置下使用“输入 = 有效 + 隔离 + 去重”；实例归并成检查、JOIN、聚合另列转换前后数量，不能硬套该公式。每条异常可有多个原因，但隔离记录只计一次。

先设计完整快照与原子发布：失败批次保留诊断信息，查询侧继续读取上一成功批次；同一数据版本重跑结果一致。之后再评估增量 upsert，不把快照重跑当成已实现 CDC 或增量数仓。

## 6. FHIR 与 DICOM 的范围

FHIR 已固定为 R4B 4.3.0，显式使用 R4B 模型。已导出 Patient、Encounter、ImagingStudy 摘要并校验；完整series需补可信StudyInstanceUID。详见 [FHIR实测](stage-c-fhir/README.md)。

患者映射 Patient；就诊映射 Encounter；影像元数据应按 ImagingStudy 等适合的资源语义设计。已有把“检查”统一转为 Observation 的示例应重新评审。后续接入 observations.csv 时再明确真实观察指标的值类型、代码与单位映射。此处是设计计划，尚未完成标准符合性验证。

Synthea 普通 CSV 样本中的影像元数据不等于实际 DICOM 文件。当前影像 CSV 测试不能替代 DICOM 解析测试。DICOM 适配器保留为独立验证项，未来需要实际文件或有明确标识的测试夹具；暂不处理像素数据。

## 7. 执行阶段与验收

| 阶段 | 工作 | 交付与通过条件 |
| --- | --- | --- |
| A：复习与盘点 | 对照入口、模块、SQL、DAG、API；解释一条记录现状 | 当前流程图、实现/未实现清单，能说明现有三个样例怎么跑 |
| B：数据剖析与建模 | 盘点 Synthea 三张主表，确定业务键、粒度、字段映射和统计口径 | 数据字典、表关系、建模草案；解释源条数与检查数差异 |
| C：小样本闭环 | 恢复环境，按确定的规则补主链路、质量处置和流转报告 | 输入到数仓再到查询可复现；各层数量对账 |
| D：可靠性验证 | 重复、缺字段、非法日期、孤儿关联、空输入、属性冲突；失败与重跑 | 自动测试与失败证据；失败不发布，重跑不重复计数 |
| E：规模与性能 | 分级生成 Synthea 数据；记录数据生成与 ETL 各自耗时 | 每表实际行数、数据量、资源情况；多次运行结果，不用单次小样本外推生产性能 |
| F：组件验证与复习材料 | Spark 对照、数据库/API 验证，最后验证 Airflow 编排 | 按组件列出已通过/未验证；整理项目讲解与真实问题复盘 |

每阶段先解释设计与结果，再进入下一阶段，避免复习过程变成看不懂的大范围代码重写。B 阶段交付见 [数据剖析与模型草案](stage-b/DATA_MODEL.md)。C 核心闭环和 FHIR 摘要导出已完成，D本轮13项可靠性扩展已通过，E首轮分级实测已完成，千人ETL通过、万人ETL受内存限制；见[第十章](html/10-scale.html)。最新状态以 [进度记录](PROGRESS.md) 为准。

## 8. 面试最终要拿得出的材料

1. 一张业务与数据流图，能讲明每层目的及粒度。
2. 一份数据集清单，能回答患者数、就诊数、检查数、字节数。
3. 一份逐层对账报告，能解释丢弃、去重、归并、关联和汇总。
4. 一条真实记录的追溯示例，能从 API/汇总回查至源文件。
5. 一份测试与性能报告，明确硬件、版本、数据规模和测试边界。
6. 三到五个实际问题案例：现象、证据、原因、修复、验证。
7. 明确哪些是亲自实现/实测，哪些是设计理解；跨行业迁移回答建立在这些真实经验上。
