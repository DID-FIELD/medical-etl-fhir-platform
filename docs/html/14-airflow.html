产物成功与任务成功是两件事

try=1：ETL → 回读/对账/哈希通过 → manifest SUCCESS
       → 验收故意抛异常 → Airflow 任务失败
try=2：找到 try=1 的 SUCCESS
       → 核验来源、代码、检查项、全部产物哈希
       → 返回同一 manifest → 任务成功

如果第二次总是从头跑，会浪费已完成的工作，也可能覆盖已有成果。若直接相信文件存在，又可能复用半成品。正确做法是按状态和完整契约验证，再决定复用或创建新尝试。

运行身份如何隔离？

Airflow run_id 可以含冒号、斜线等文本，工作流将它哈希为目录名；try_number 形成 attempt-0001 等独立目录。不同运行不混用产物，同一次失败尝试不可覆盖，后续尝试可建新目录。

发现的状态行为
未有结果创建新尝试，运行 ETL
先前 FAILED / 未完成保留现场；新尝试独立执行
有效 SUCCESS核验通过后复用，不生成第二份产物
损坏 SUCCESS / 来源或代码不匹配明确失败，不能悄悄重算掩盖问题

核验包含源归档、基准 manifest、生日口径、代码哈希、26 项检查、14 组零差异以及递归文件清单和哈希。路径合法也要检查，不能只相信 worker 返回任意文件名。

为什么要独立 worker？

Airflow 使用自身受约束的虚拟环境；PythonOperator 调用 worker Python 子进程执行 Spark。Spark/FHIR 依赖保留在 worker 环境，XCom 只传 manifest 路径，不传整张数据表。项目只读挂载到 WSL，运行目录可写。

配置包括归档、基准、输出根目录、worker Python 和生日偏移。新验收创建独立 AIRFLOW_HOME 和元数据库，不影响已验收会话或正式发布。

三层验收各证明什么？

  1. DagBag：DAG 可导入，任务集合与依赖正确。
  2. dag.test：依赖和任务能在测试执行中跑完。
  3. 真实 scheduler：SequentialExecutor 实际驱动任务；故障注入后 try=2 成功，两个回执指向相同 manifest 和哈希，未创建 attempt-0002 产物。

Stage J 千人得到 1,159 患者、70,229 就诊、2,239 检查、89,354 实例，14 组零差异、26 项检查通过。工作流专项为 21 passed；没有本轮 RSS 测量。串行成功不证明并发 worker 竞争时已有锁协议。

Stage L：数据库回执有效，还要检查实际内容

FHIR 重试核验导出 manifest、资源数量和文件哈希。数据库重试使用只读 REPEATABLE READ 事务，以 SQLite 磁盘索引逐行核对九表、ODS 和账本，保留重复次数；仅看数量不能发现同数量篡改。

数据库提交后 worker 若来不及写成功回执，新尝试会返回 ALREADY_LOADED 后重新核对，不假定任务失败意味着回滚。两下游各自恢复，其中一个失败不等于另一个回滚。

本机 Spark/FHIR 在 WSL，数据库使用 Windows worker，wslpath 转换共享 F 盘路径；同一文件可能有 /mnt/f 与只读 bind mount 两个路径，adapter 用文件身份核验后返回配置的产物路径。PostgreSQL 仍只监听 Windows localhost，未开放网络端口。每个 run 派生独立 schema，正式发布未变。

千人四任务 scheduler：输入和 ETL 各 try=1，FHIR 和数据库各 try=2；回执路径/哈希相同，无第二份消费者产物。73,627 个 FHIR 资源等价、数据库 11 组内容一致、132 次串行 API 通过。该千人阶段没有 RSS 或万人新 DAG 结论；万人新链路另见下方 Stage M。验收报告。

自动重试不能替代明确的资源配置

Stage M r3 的生产 Spark 首次报 Java heap space，第二次成功，生产四任务 DAG 最终通过。但随后真实 scheduler 的两次 Spark 尝试均因同类错误失败，下游显示 upstream_failed，整轮验收仍是 FAILED。

运行时采集确认 JVM 参数为 -Xmx1g。错误发生在缓存反序列化；一次重试成功不代表该资源配置长期稳定。新的验收入口用 --spark-driver-memory 显式配置堆，默认 2g，并在总报告中保存配置。r4 使用 2g 后 Spark 首次通过，但数据库消费在 1800 秒超时，后续主机关机使整轮中断；r5 沿用 2g，生产通过，但真实 scheduler 被验收器的 SQLite 状态读取锁冲突中断。后续 r6 独立完整验收通过，详见下文。各轮保留原失败目录，不修改业务数据、对账规则或消费者超时。

JVM 堆大小只是一项运行参数，不等于进程树 RSS，更不等于 Spark、Python worker 和 PostgreSQL 的总内存。历史 Python 500 MiB 测量不能套到这轮 Spark 验收。r3 失败证据。

状态查询失败，不等于业务任务失败

r5 的 Spark 仍在计算时，验收器读取 Airflow 元数据库遇到 database is locked。异常向外传播，finally 清理逻辑终止 scheduler，留下 RUNNING 产物。只看总报告的 OperationalError 或遗留状态，都无法判断 Spark 当时的真实情况。

修复只重试 SQLite BUSY/LOCKED：关闭失败会话，下次重新读取，并继续检查 scheduler 存活和原总截止时间。其他数据库错误仍直接失败。真实 Airflow 环境 13 项测试覆盖实际独占锁释放、持续锁定超时、进程退出和非锁错误传播；r6 实际恢复了 8 次锁冲突，最终整轮通过。

这说明验收器本身也需要处理短暂故障；不是忽略全部 OperationalError，也不是取消超时。r5 原始 FAILED 报告和日志保留。诊断与失败日志。
