ODS 行号为什么不能重编？

原始 CSV：source_row 1 = A，source_row 2 = B
Parquet 分区读取：先 B，后 A
错误做法：enumerate → B 被标成 1，A 被标成 2
正确做法：读取保存的 source_row → B 仍是 2，A 仍是 1

数量仍为 2，错误血缘却会让 API 指向错误源记录。因此消费器取 ODS 的 source_row + raw map，而不是分区遍历序号。测试专门逆转物理行序，数据库再对原字段、源哈希和行号逐行核对。

源文件变化要在提交前拦住

  1. 只接受 SUCCESS manifest，校验目录完整文件清单及哈希；缺失、额外、损坏文件和符号链接被拒绝。
  2. 按批读取，但数据库只开一个事务。ODS、处置账本和九表写完后，做 SQL 数量、关联、覆盖及源行范围检查。
  3. 提交前再次核验源 manifest 和文件，防止读取期间发生变化，再切换隔离 schema 内的 current。

受控测试在加载中增加文件，触发清单不一致，新事务全部回滚，旧批次仍可读。分批执行不等于分批提交。

FHIR 不能用文件字节相同代替业务等价

分区读取顺序可以改变 NDJSON 行序，所以先分别导出，再按资源类型、ID、规范化内容比较。SQLite 主键确保 ID 唯一，双向比较确保没有漏出或多出。这样既识别语义错误，也不会把单纯排序变化误报为错误。

Patient/Encounter/ImagingStudy 的映射不变。完整实例仍留在数仓；缺可信 StudyInstanceUID 时继续输出摘要，不猜 UID 或像素 endpoint。

事务已提交，为什么验收仍未完成？

Stage M 首轮 r1 的 Spark 已成功，数据库加载也提交了事务，但消费者回执停留在 RUNNING。Windows 事件记录随后发生宿主机关机；重启后的 PostgreSQL 进行了异常关闭恢复。只读查询发现隔离 schema 已有该 run，而完整内容核验、下游重试和总验收没有成功报告。

三个状态需要分开：数据库提交意味着事务对外可见；消费者 SUCCESS 还需要完整内容验证及持久化回执；整轮验收 SUCCESS 进一步要求 DAG、重试、FHIR、API 和正式指针保护全部通过。不能把存在 pipeline_runs 记录等同于整轮成功，也不能只凭遗留 RUNNING 判断进程还活着。

临时索引的位置也会影响导出

Stage M 的 r2 首次 FHIR 导出在 1800 秒超时，第二次也未完成，不能只归因于稍后的宿主机关机。现场保留 Patient 和部分 Encounter，以及位于输出目录中的 SQLite 暂存索引。

独立诊断保持相同 10 万条输入、表结构和 8 MiB SQLite 缓存：WSL 的 F 盘挂载上写入耗时 21.05 秒，Linux 临时目录为 2.43 秒。这是局部 I/O 对照，不能当作完整导出的加速比。修复将随机访问的 SQLite 索引放到 worker 系统临时目录；NDJSON 和成功回执仍写到共享输出目录。

模型、唯一性、引用、NDJSON 回读、来源哈希及 1800 秒任务超时均保留。修复后独立万人消费在 742.634 秒内完成；708,747 个资源与 Python 参考逐条一致，保持同 run 绑定，重试复用同一成功回执且没有第二份产物。该耗时不是局部 I/O 对照的加速比；独立消费通过仍需另做完整 DAG 验收。诊断、修复与验证记录。
