把零散记录变成能解释的患者概览

回答：这位患者在哪次就诊中做了哪些检查？有几次？最近一次是什么时候？

Synthea 提供合成患者、就诊和影像实例记录。项目保留原始字段，治理重复、冲突和无效关联，再按患者、就诊、检查、序列、实例分别建模，提供查询与 FHIR 摘要资源。使用的是合成数据，实测环境是本机。

业务结果患者检查概览、UTC 日×模态检查量。
工程证据逐行对账、源记录追溯、失败回滚、重试复用。
学习目标讲清数据为何变多或变少，以及每一步怎样验证。

两条执行路径，共用一套业务口径

三张 CSV → ODS完整原始字段、文件 SHA-256、逻辑 source_row。
↓
Python streaming分批读入、SQLite 暂存、按关联组处理，输出 JSON / 单文件 Parquet。完整 Spark严格 CSV adapter → Parquet；Spark window/groupBy/join 质量治理与九表。
↓ 同口径对账
成功快照 → 公共读取器旧 JSON 或 Spark 目录分批读取；保持业务键与源行号。
PostgreSQL → API单事务加载、SQL 对账、批次指针切换、患者与血缘查询。FHIR R4B 摘要Patient / Encounter / ImagingStudy → NDJSON，校验 ID、引用和回读。

这是已实现的处理与消费关系。完整 Spark DAG 现已编排输入校验、完整 ETL、FHIR 和隔离 PostgreSQL；Stage L 千人及 Stage M 万人真实调度与两个下游故障重试通过。见两条 Airflow 链路。

怎样复核这次万人成功？

  1. 看验收报告：生产 dag.test 和真实 scheduler 必须都成功，输入/Spark 为 try=1，两个消费者为 try=2。
  2. 看重试证据：两次消费者回执必须指向相同 manifest 和哈希；不能以“重跑也成功”代替复用。
  3. 看内容证据：11 组数据库逐行零差异、708,747 个 FHIR 资源等价，以及 132 次串行 API 检查。
  4. 看独立复核：源与代码绑定、消费产物哈希、两次 Spark 完整清单都通过后，才更新完成度。
