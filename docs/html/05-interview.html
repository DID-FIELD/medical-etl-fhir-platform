60 秒讲清当前项目

“我用 Synthea 合成数据做了可复现的医疗数仓原型，按患者、就诊、检查、序列和实例建模，并保留源行与质量处置账本。万人归档约 173 万源行，Python 流式 ETL 约 393 秒，采样内存峰值约 281 MiB。完整 Spark 在同一口径下对九表、ODS 和质量账本做双向逐行对账，全部一致。我也验证了 Airflow 失败后复用成功产物，以及千人和万人 Spark 产物进入数据库、FHIR 和 API 的内容一致性。”

接着补边界：“Spark 是单机 local[2]，万人约 2.52 GiB，时间包含对账；两条调度链路的规模分别记录，新完整 DAG 及 FHIR/数据库下游已通过千人和万人验收。”

追问一：数据量到底是多少？

万人归档为 11,476 位患者、677,836 次就诊、1,036,348 个影像实例；实例归并为 19,435 次检查，保留 8,473 位零检查患者。千人消费验收另用 1,159 位患者的归档。不要把生成档位、实际人数、检查数和实例数混称“数据条数”。

为什么历史样本是 478 行，检查只有 413？

那是另一个小样本的实例与检查粒度差异：65 次检查有两个实例。它说明一对多关系，不表示丢弃了 65 条坏数据。

追问二：怎样证明 Spark 写对了？

比较同一归档、同一生日偏移的 Python 基准。九表、ODS、处置账本、warnings 共 14 组双向多重集差异都为 0，另验证 26 项粒度、外键、源记录账平和聚合检查。15 组转换参数用例覆盖重复、冲突、父级异常和元数据不一致等情形。

自然数据里没有异常，不能证明异常规则有效；故障 fixture 与正常规模归档是不同证据。各批次测试不简单累加成一个完整回归总数。

追问三：讲一个真实修复

问题处理与验证边界
万人全量读取超内存改为分批、磁盘暂存及连通组处理；同一归档成功，采样 280.76 MiB超大关联组仍可主动失败，不保证任意输入恒定内存
生日与事件时区不同显式 +08:00 生日口径，千人 45 条误隔离恢复；事件仍 UTC不能对未知来源自动猜时区
分区顺序破坏源行号消费者使用 ODS 保存的 source_row；乱序 fixture 和数据库逐行对账通过不是用分区读入序号重建血缘
ETL 成功但 Airflow 任务失败注入成功后异常；try=2 核验并复用 try=1 manifest，无第二份 ETL验证千人串行调度，不是并发写入协议

用 r5 → r6 讲清一次完整排障

“r5 生产 DAG 已成功，但验收器读取 Airflow 元数据库时遇到 SQLite 锁冲突，异常触发清理并终止 scheduler。当时 Spark 仍在计算，所以我把问题定位到状态读取，而没有把遗留 RUNNING 当作业务失败原因。”

“修复只对 BUSY/LOCKED 重新建立会话并重试，同时保留原截止时间、scheduler 存活检查和其他错误传播。实际锁释放、持续锁定超时等 13 项测试通过后，用新 r6 完整复验。r6 恢复了 8 次锁冲突，最终两个消费者故障后 try=2 复用，内容与 API 全部通过。”

回答时分清：13 项是修复测试，8 次是本轮观测事件；两者都不是长期可靠率。历史 Stage F 的数据库/API OperationalError 尚未定因，不能用这次 Airflow SQLite 根因替代。日志与处理逻辑 · 完整验收范围。

追问四：FHIR 和性能可以说到哪里？

万人 Python 快照导出 708,747 个 R4B 摘要资源；千人和万人 Spark 与 Python 导出分别为 73,627 和 708,747 个资源，按身份和内容双向等价。没有可信检查级 DICOM UID，不编造 series 层级、identifier 或像素 endpoint。

Python 的 393 秒与 Spark 的 283 秒范围不相同，不能直接宣称固定倍数加速。数据库 132 次请求为串行 ASGI 功能验收，不是网络并发吞吐。FHIR 模型校验不等于官方 Validator、术语服务或 FHIR Server 验收。

没有闭环的事项也要讲清

历史万人数据库加载已提交，但随后首次 API 出现 OperationalError，复验成功，具体根因尚未确认。保留这个边界，不编造网络或连接池根因。新完整 Spark DAG 已接入消费者并完成千人/万人调度；独立备份与并发负载仍没有新结论。
