“千人/万人”是生成配置档位，实际患者行数以归档清单为准。不要把 108 位小样本的 413 次检查与万人 1,036,348 个实例放进同一个守恒等式。

历史小样本：478 → 413 → 96

478 个实例属于 413 次检查，涉及 96 位有影像患者。348 次检查各 1 个实例，65 次各 2 个实例，因此 348 + 65×2 = 478。少了 65 个“行位置”是聚合粒度变化，不是丢了 65 条坏数据。

患者总数为 108，另有 12 位零影像患者；完整维表必须保留他们。早期只含 96 位影像患者的探索结果，是后续扩展患者覆盖的历史对照。

第一层证明：同粒度输入守恒

输入记录 = accepted + duplicate + quarantined

教学例：1,000 条输入 = 950 有效 + 10 重复 + 40 隔离。一条记录失败两条规则，只计一次隔离；warning 单独记录，不加进互斥处置等式。

在数据库中，还要检查 ODS 数量、源行号唯一性及范围、处置账本数量；保留的模型行应能匹配 accepted 血缘。只核对总行数，发现不了源行号被分区顺序重新编号的问题。

第二层证明：跨粒度数量和关联

  • 患者汇总的 exam_count 总和 = 检查事实行数。
  • 日×模态的 exam_count 总和 = 检查×模态桥表行数。
  • DIM、患者 DWS、患者 ADS 覆盖同一组有效患者，含零检查者。
  • 检查与就诊患者必须一致，实例指向合法的检查和序列。

万人基准保留 8,473 位零检查患者。只保留影像队列，即使检查数量不变，患者覆盖也已错误。

第三层证明：双向多重集逐行对账

实际 EXCEPT ALL 期望 → extra
期望 EXCEPT ALL 实际 → missing
两个方向都为 0，才说明内容和重复次数相同。

教学反例：期望 [A,A,B]，实际 [A,B,B]。两边总数都是 3，去重集合都是 {A,B}，但 A/B 的次数错了。EXCEPT ALL 保留重数，普通 distinct 或总数对比会漏掉它。

验收比较范围结果
完整 Spark → Python九表 + 三份 ODS + dispositions + warnings，14 组千人/万人双向零差异；另有 26 项内部检查
Spark/Python → PostgreSQL九表 + source_records + row_dispositions，11 组Stage K 千人 SQL 双向零差异；Stage M 万人用 SQLite 保留重复次数逐行核对，11 组一致
Spark/Python → FHIR类型 + ID + 规范化资源内容千人 73,627、万人 708,747 个资源等价；唯一 ID 单独约束

分区顺序不同不代表内容不同。NDJSON 字节哈希适合验证同一产物未变；跨执行路径比较应按资源身份与内容核对。证据：Stage I、Stage K。

性能数据也必须有口径

Python 万人流式 ETL 392.618 秒；完整 Spark 283.201 秒包含输出回读和基准对账，两者范围不一致，不能直接计算纯 ETL 加速比。失败前 5.742 秒不是成功处理万人所需时间。ALREADY_LOADED 的复验耗时也不是重新入库耗时。

测试结果分批记录，可能重叠，不把 21 项工作流、31 项旧消费回归与 10 项新消费测试相加后声称单次完整回归通过。
