实际问题一：重复表头会悄悄改字段

Id,BIRTHDATE,DEATHDATE,GENDER,GENDER
p1,1980-01-01,,M,F

以前CSV读取器会留下后一个GENDER，M被F覆盖，后续格式与枚举校验可能都通过。故障测试发现它没有报错。

修复：先检查列名是否唯一。重复表头直接拒绝本批次，失败清单记录原因，旧成功批次继续可用。

实际问题二：清单列什么，才检查什么

旧加载器会逐项校验清单中的哈希，但未确认清单包含全部必需产物。如果清单漏了dim_patient.json，数据库加载仍会继续。

修复：先确认9张模型表的JSON与Parquet、3个ODS、处置账本全部具备哈希，再逐项校验。缺项时在连接数据库前拒绝。它防止漏检和意外损坏，并不证明文件来自可信签名者。

故障放在哪一层？

输入CSV重复表头、行宽不一致、来源文件不唯一 → 拒绝整批，旧发布结果保持
↓
质量与关联非法生日、缺时区、倒置时间 → 隔离错误父级与影像，处置账本仍逐行对账
↓
文件写入与发布Parquet中途写入失败、指针替换失败 → FAILED清单保留，新run_id可重跑
↓
数据库加载篡改、漏哈希、失败清单 → 连接前拒绝；写入后段异常 → 整批事务回滚
↓
API读取新批次尚未提交或已失败 → 继续读旧批次；重试提交成功 → 切换新批次

一次完整的失败与恢复演练

  1. 文件和数据库先发布old批次，作为可靠基线。
  2. 准备new文件快照；数据库开始加载它，已写入前面多张表。
  3. 在ADS写入前，用独立API连接读取：仍显示old。
  4. 注入异常，使new事务失败；检查所有相关表，new记录数均为0。
  5. 撤销故障，重新加载同一new文件，发布成功。
  6. 再次加载old只返回已加载，不把当前版本倒退；同ID清单被改变则拒绝。
old/new是测试批次名，测试在临时文件与隔离schema内运行。这里测的是事务未提交期间的另一连接读取，不是多发布者并发压力。

文件成功，数据库失败怎么办？

时点文件当前批次数据库/API当前批次
原基线oldold
新文件完成，连接数据库失败file-readyold
连接恢复，补加载成功file-readyfile-ready

这是两个发布步骤，不是分布式事务。恢复时读取已有SUCCESS目录并重新加载；测试确认恢复前后该目录每个文件的哈希完全相同，无需重新跑ETL。

恢复命令与适用条件
.\.venv\Scripts\python.exe -m scripts.local_postgres start
.\.venv\Scripts\python.exe -m src.database.synthea_store --run-dir output/synthea/runs/stage-c-verified

上述目录是当前成功批次，重复执行会返回已加载。实际故障时替换为对应SUCCESS目录；不要加载FAILED目录，不要修改历史清单绕过检查。

面试回答：你实际遇到过什么问题？

“我做过分层故障注入，发现重复表头会覆盖字段，导入清单漏哈希也没有被拒绝。修复后，对入口、文件发布、事务回滚和恢复重试都加了测试。”

“数据库写到后段失败时，另一连接仍能读旧批次，回滚后新批次没有残留。文件成功但数据库连接失败时，可以直接补加载已有快照。这样的验证比只说‘加了try/except’更能说明恢复机制。”
