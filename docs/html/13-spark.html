这次 Spark 从 CSV 开始

早期 Spark 只从已有模型重算三张汇总表。完整实现从三张 CSV 接入，覆盖原始数据保留、冲突治理、父级关联、检查级隔离和九表输出。两者不能共用“完整 ETL”这个结论。

严格 Python CSV adapter保留所有字符串字段、逻辑 source_row 和原始行签名；分批落 Parquet。
↓
Spark 质量治理window/groupBy 识别重复与冲突；join 有效父级；级联隔离不完整检查。
↓
九表 + ODS + 账本 + warnings先持久化，再回读检查、对照 Python 基准，最后记录文件哈希。

Python adapter 负责无损解析；Spark 负责主要关系运算。不能说全部解析都由 Spark 原生 CSV 完成，也不能把父表全量 collect 到 Python 后称为 Spark 关联。

为什么源行号与签名不能省？

CSV 引号内换行仍是一条记录。source_row 从数据记录 1 开始，不含表头；Spark 分区 ID 或读取顺序不等于该逻辑行号。原字段按参考 JSON 规则排序序列化后做 SHA-256，使同键的任一字段差异都能触发冲突。

同一 INSTANCE_UID：
第一次 A、第二次 A、第三次 B（一个原始字段不同）
 → 这个键的所有记录都冲突隔离
不是只丢第三次，也不是让第一次永远保持 accepted。

治理必须考虑同键全部记录。患者/就诊只有 accepted 才能作为有效父级；检查的任一实例无效会导致整项检查隔离。warnings 保留重数，不能只筛最终 accepted 后生成。

三类证明逐层执行

  1. 内部检查：九表业务键、父子外键、输入账平、accepted 血缘、患者覆盖、检查与桥表计数守恒，共 26 项。
  2. 独立基准：九表、三份 ODS、dispositions、warnings 共 14 组双向 EXCEPT ALL。排除不同 run_id，保留 reasons 顺序、warnings 重数和 ODS raw 内容。
  3. 产物绑定：源归档、基准 manifest、代码及产物哈希留在运行清单中；回读后才标记 SUCCESS。

总数相同只能作为第一步。正确性对账的教学反例见第 3 章。

代码与失败现场怎么读？

代码重点
synthea_ingest.pyCSV 校验、逻辑行号、原字段和签名
synthea_rules.py / synthea_etl.py逐行规则与 Spark 关系治理、九表转换
synthea_full.pyRUNNING / FAILED / SUCCESS、禁止覆盖、回读与基准对账

Windows 首次 UDF 执行出现 worker WinError 10038 / EOFException，根因未定；完整 Spark 在 WSL 中通过。不要把环境失败改写成业务数据对账失败，也不要删除失败目录让记录看起来全成功。
